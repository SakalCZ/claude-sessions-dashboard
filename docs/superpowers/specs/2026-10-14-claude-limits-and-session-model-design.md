# Claude Usage Limits and Per-Session Model — design

Date: 2026-10-14
Status: approved in brainstorming, awaiting spec review
Builds on: `2026-10-08-attention-queue-and-resources-design.md` (system bar, alerts, notifier, settings merge)

## 1. Purpose

The user runs several Claude Code sessions at once on a Claude subscription. Two additions to the dashboard:

1. **Usage limits block.** How much of the 5-hour and the weekly limit is used, when each resets, the weekly limit of
   individual models (e.g. Fable) and the extra-usage credits, with a banner and a macOS notification before a limit
   runs out.
2. **Model and effort per session.** Every session row shows the model and the reasoning effort the session runs on.

### Success criteria

- While any interactive session is running, the limits block is at most one Claude response behind what Claude Code
  itself knows about the 5-hour and the weekly window. An idle session that redraws its status line with older values
  never makes the block go back.
- The block always says how old its data is; data older than 30 min is visibly marked stale.
- A window at ≥ 80% shows a warning banner and one macOS notification; ≥ 95% is critical; both repeat at most once
  per `resource_reminder_after_s` while the state lasts. A window that has reset never alerts.
- Every session row with at least one Claude response shows e.g. `Opus 5.5 · xhigh`, including sessions that are not
  running. Searching `fable` finds the sessions that ran on Fable.
- The user's own status line keeps working exactly as before.

### Out of scope (YAGNI)

- Calling Anthropic's usage endpoint (`/api/oauth/usage`) or reading the OAuth token. The dashboard makes no network
  calls.
- History or charts of usage over time; only the current state is shown.
- API-key, Bedrock, Vertex and gateway spend limits (`rate_limits.spend_limit`); the user is on a subscription.
- Showing a `/model` or `/effort` switch before the session's next response.
- Model and effort in the attention queue; they are on the session rows only.

## 2. Verified facts (2026-10-14, Claude Code 2.1.299, on the user's machine)

- **Status line input.** Claude Code's built-in status line documentation (in the binary) describes an optional
  `rate_limits` object on the status line's stdin: "Claude.ai subscription usage limits … Only present for
  subscribers … after first API response, while at least one window is present":

  ```
  "rate_limits": {
    "five_hour": { "used_percentage": number, "resets_at": number },   // 0-100, Unix epoch seconds
    "seven_day": { "used_percentage": number, "resets_at": number },
    "spend_limit": { … }                                              // gateway only, out of scope
  }
  ```

  Each window is "present only while the API reports it and its resets_at has not passed". The same input carries
  `model` and `effort.level` per session.
- **Hooks do not carry limits.** None of the captured hook payloads (`tests/fixtures/hooks/`) has `rate_limits`.
- **Claude Code's own cache.** `~/.claude.json` has `cachedUsageUtilization`, written by Claude Code after it fetches
  the usage endpoint (throttled, observed fetched at session start):

  ```
  "cachedUsageUtilization": {
    "fetchedAtMs": 1791984333901,
    "accountUuid": "<uuid>",                       // equals oauthAccount.accountUuid of the signed-in account
    "utilization": {
      "five_hour": { "utilization": 32, "resets_at": "2026-10-14T16:49:59.701245+00:00", … },
      "seven_day": { "utilization": 27, "resets_at": "2026-10-19T04:59:59.701269+00:00", … },
      "extra_usage": { "is_enabled": true, "monthly_limit": 1000, "used_credits": 0, "currency": "EUR",
                       "decimal_places": 2, "spend_limit_reached": false, … },
      "limits": [
        { "kind": "session", "percent": 32, "resets_at": "…", … },
        { "kind": "weekly_all", "percent": 27, "resets_at": "…", … },
        { "kind": "weekly_scoped", "percent": 3, "resets_at": "…",
          "scope": { "model": { "id": null, "display_name": "Fable" }, "surface": null }, … }
      ],
      …
    }
  }
  ```

  It is undocumented and may change in any release. `~/.claude.json` is ~120 KB.
- **The account** is a Max subscription (`oauthAccount.billingType` `stripe_subscription`), so `rate_limits` is
  expected in the status line input.
- **Transcripts.** Every `assistant` record has `message.model` (e.g. `claude-opus-5-5`) and a top-level `effort`
  (e.g. `xhigh`). Error messages generated by Claude Code itself use the model `<synthetic>`.
- **The user's status line** is `{"type": "command", "command": "bash ~/.claude/statusline-command.sh"}`. The script
  reads stdin with `input=$(cat)` and uses `$(pwd)`.

### To verify before building on it (plan Task 1, the spike)

A temporary copy of the tap (writing raw stdin to the scratchpad) confirms:

- that `rate_limits` with `five_hour` and `seven_day` actually arrives in this account's status line input, and how
  often the status line runs while Claude is streaming;
- which shell Claude Code runs the status line command in, so the tap runs the original command the same way;
- whether a running session picks up a changed `statusLine.command`, or only new sessions;
- that an empty status line output takes no line in the Claude Code UI (needed when the user has no status line);
- the tap's added latency per render (target: < 100 ms);
- how often `cachedUsageUtilization.fetchedAtMs` advances during a normal working hour;
- with one session idle and another working: whether the idle one redraws its status line, and with which values
  (each Claude process reports the limits of its own last API response);
- how far the status line's `resets_at` lies from the cache's `resets_at` for the same window (sets the same-window
  tolerance in §6).

The spike's findings go into the plan's ledger. If a fact differs, the smallest change that keeps this spec's
behavior is made and recorded.

## 3. Overview

```
Claude Code ──stdin──▶ hook/statusline_tap.py ──▶ <data>/rate_limits/<session_id>.json ─┐
                         │                                                              ├─▶ limits.py ─▶ App.snapshot()["limits"]
                         └─▶ original status line command (stdout)                      │      │
~/.claude.json (cachedUsageUtilization) ────────────────────────────────────────────────┘      └─▶ alerts ─▶ Notifier, #alerts

~/.claude/projects/**.jsonl ──▶ sessions.py (model, effort) ──▶ row["model"], row["model_label"], row["effort"]
```

`<data>` is `~/Library/Application Support/claude-dashboard`, overridable with `CLAUDE_DASHBOARD_DATA_DIR` exactly
like `hook/claude_hook.py`.

## 4. Status line tap (`hook/statusline_tap.py`)

Standalone, standard library only, like `hook/claude_hook.py`. Claude Code runs it as the status line command.

1. Read all of stdin as bytes.
2. Try to record the limits (any exception is swallowed, nothing is printed):
   - parse the bytes as JSON; take `rate_limits` if it is an object with at least one of `five_hour` / `seven_day`,
     and `session_id` if it matches `^[0-9a-f-]{36}$` (the hook's check); otherwise record nothing;
   - read `<data>/rate_limits/<session_id>.json`; write a new one only if the stored `rate_limits` differ or the
     stored `captured_at` is older than 60 s;
   - write atomically (temp file in the same directory, `os.replace`):

     ```json
     {"captured_at": "2026-10-14T13:40:02Z", "session_id": "…", "rate_limits": {"five_hour": {…}, "seven_day": {…}}}
     ```

     `rate_limits` is stored as received. Each session writes only its own file. Each Claude process reports the
     limits of its own last API response, so an idle session's file can hold older values than a working one's; the
     merge in §6 handles that.
3. Read `<data>/statusline.json` (`{"command": "<original command>"}` or `{"command": null}`). If there is a command,
   run it with the same stdin bytes, the inherited environment and working directory, in the shell confirmed by the
   spike; write its stdout bytes to our stdout, let its stderr through, and exit with its exit code. Without a command,
   print nothing and exit 0. A missing or unreadable `statusline.json` counts as no command.

The tap must never break the status line: step 2 cannot affect step 3.

## 5. Install and uninstall (`settings_merge.py`, `launchd/*.sh`)

The tap command is `"<python3>" '<APP_DIR>/hook/statusline_tap.py'`; the marker that identifies it is
`claude-dashboard/app/hook/statusline_tap.py` (same scheme as the hook marker).

The CLI becomes:

```
settings_merge.py install   <settings.json> <hook-command> <tap-command> <statusline-store>
settings_merge.py uninstall <settings.json> <statusline-store>
```

One call changes hooks and the status line together, so there is one backup per run.

**Install (wrap):**

- `statusLine` missing → store `{"command": null}`, set `statusLine` to `{"type": "command", "command": <tap>}`.
- `statusLine.command` already contains the marker → leave `statusLine` and the store unchanged.
- Otherwise → store `{"command": <original>}`, replace only `statusLine.command`; keep every other key (`padding`, …).
- `statusLine` not an object, `type` not `"command"`, or `command` not a string → `MergeError`, nothing is changed.
- The store is written (atomically) before `settings.json`, so the tap never runs without it.

If the user later replaces the status line (by hand or with `/statusline`), the tap is gone until the next
`install.sh`, which wraps the new command. The README tells the user to change the status line by editing their own
script (e.g. `~/.claude/statusline-command.sh`), which the tap keeps running.

**Uninstall (unwrap):**

- `statusLine.command` without the marker → leave it.
- With the marker and a store with a command → restore that command.
- With the marker and a store with `null`, or no readable store → remove `statusLine`.
- Delete the store after `settings.json` is written.

`install.sh` copies `hook/statusline_tap.py` and the new `limits.py`; both scripts pass the new arguments.

## 6. Limits (`limits.py`)

`LimitsReader(data_dir, claude_json_path, config, clock, tz)` with `snapshot() -> dict`. Each file is re-read only
when its `(mtime, size)` changes. Every missing, malformed or unexpected value means "not available" for that part
only; nothing raises. Claude Code rewrites `~/.claude.json` often; when it cannot be parsed (e.g. caught mid-write),
the last good parse is kept and the file is retried on the next snapshot.

**From the tap** (every `<data>/rate_limits/*.json`): `five_hour` and `seven_day` with `used_percentage` (number) and
`resets_at` (epoch seconds); `as_of` = `captured_at`; `source` = `"statusline"`. Files not modified for 8 days are
deleted (no window lasts longer than 7 days).

**From the cache** (`~/.claude.json`), only if `cachedUsageUtilization.accountUuid` equals
`oauthAccount.accountUuid`; `as_of` = `fetchedAtMs`; `source` = `"cache"`:

- `five_hour` / `seven_day` from `utilization.<window>.utilization` and `.resets_at` (ISO 8601);
- per-model weekly windows from `utilization.limits[]` entries with `kind == "weekly_scoped"` and a string
  `scope.model.display_name`, using `percent` and `resets_at`; kind `weekly:<display_name>`;
- extra usage from `utilization.extra_usage`: `enabled` = `is_enabled`, `used` = `used_credits / 10**decimal_places`,
  `limit` = `monthly_limit / 10**decimal_places`, `currency`, `limit_reached` = `spend_limit_reached`.

**Merge**, per window kind, over every candidate from the session files and the cache. Usage within a window only
goes up, so the highest value is the most recent one, whichever session reported it:

1. Drop candidates whose `resets_at` is in the past.
2. The window with the latest `resets_at` wins (a later reset means a newer window). Two `resets_at` values within
   600 s of each other are the same window (the status line rounds to seconds, the cache does not; the spike confirms
   the distance).
3. Within that window, the highest `used_pct` wins.
4. `as_of` is the newest `as_of` among the candidates of that window with that `used_pct`; `source` is that
   candidate's source.

Result:

```json
{
  "windows": [
    {"kind": "five_hour", "label": "5h", "used_pct": 32, "resets_at": "2026-10-14T16:49:59Z",
     "as_of": "2026-10-14T13:40:02Z", "source": "statusline", "level": "normal"},
    {"kind": "seven_day", "label": "Week", …},
    {"kind": "weekly:Fable", "label": "Week · Fable", …}
  ],
  "extra_usage": {"enabled": true, "used": 0.0, "limit": 10.0, "currency": "EUR", "limit_reached": false,
                  "as_of": "…"},
  "as_of": "<newest as_of of the windows, or null>",
  "alerts": [ … ]
}
```

Order: `five_hour`, `seven_day`, then the per-model windows by label. `extra_usage` is `null` when the cache has none.

**Levels and alerts:** `level` is `critical` at `used_pct >= limit_critical_pct`, `warn` at
`>= limit_warn_pct`, else `normal`. Each `warn`/`critical` window yields an alert:

```json
{"kind": "limit:five_hour", "level": "warn", "title": "Claude limits: warn",
 "message": "Claude 5h limit at 86% · resets 18:50"}
```

The message is `Claude <label> limit at <used_pct>% · resets <time>` (e.g. `Claude Week · Fable limit at 81% · …`); at
`used_pct >= 100` it reads `Claude 5h limit reached · resets 18:50`. The reset time is local time `HH:MM`,
prefixed by the weekday (`Mon 06:59`) when it is not today.

**Config** (`config.py` defaults): `limit_warn_pct: 80`, `limit_critical_pct: 95`.

## 7. Server and notifier

- `App` gets a `LimitsReader`; `snapshot()` adds `"limits": limits.snapshot()` to the payload.
- `App.tick()` passes `system alerts + limits alerts` to **one** `notifier.check_alerts` call. `check_alerts` treats
  every kind missing from a call as cleared, so two separate calls would reset each other.
- `Notifier.check_alerts` uses `alert.get("title")` as the notification title and falls back to the current
  `Mac resources: <level>`.

## 8. UI

A new `#limits` line right below `#system`, in the same style; its class is the worst window level
(`F.worstLevel`):

```
Claude limits  5h ████░░░░░░ 32% · reset 18:50 (in 1 h 9 min)  │  Week ███░░░░░░░ 27% · reset Mon 06:59
               │  Week · Fable 3%  │  Extra usage €0 / €10  ·  updated 2 min ago
```

- 5h and Week get a small CSS meter; per-model windows show the percentage only. Meter colors follow the window level.
- `updated … ago` uses `limits.as_of`. Older than 30 min → the line is greyed out and says `(stale)`.
- A window or the extra usage whose own `as_of` is older than 30 min (cache-only parts such as `Week · Fable`) is
  greyed out and gets an age suffix, e.g. `Week · Fable 3% (2 h ago)`.
- No windows and no extra usage → `Claude limits: no data yet`.
- Clicking the line toggles a detail table (like the system bar): per window the exact reset time, `as_of` and
  `source`.
- Limit alerts are rendered in `#alerts` together with the system alerts.
- New `filter.js` helpers, covered by `tests/js/test_filter.js`: `formatCountdown(resetsAt, now)` (`in 1 h 9 min`,
  `in 4 d 15 h`, `in 3 min`) and `formatReset(resetsAt, now)` (`18:50` today, otherwise `Mon 06:59`).

## 9. Model and effort per session (`sessions.py`, UI)

- `_SessionParser._line`: for every `assistant` record without `isSidechain`, if `message.model` is a non-empty string
  other than `<synthetic>`, set `model` to it and `effort` to the record's `effort` if it is a string, else `None`.
  Effort is replaced together with the model, so a model without effort clears it.
- `Session` gets `model` and `effort`; the row gets `model`, `model_label` and `effort`.
- `model_label(model_id)`: an id that does not start with `claude-` stays as it is. Otherwise drop the `claude-`
  prefix, a trailing `[…]` and a trailing `-YYYYMMDD`; split on `-`; the first alphabetic part is the family
  (capitalized), the numeric parts joined with `.` are the version:
  `claude-opus-5-5` → `Opus 5.5`, `claude-sonnet-4-5-20250929` → `Sonnet 4.5`, `claude-3-5-haiku-20241022` →
  `Haiku 3.5`. No alphabetic part → the raw id. `None` → `None`.
- Row second line: `<branch> · <worktree> · 12 prompts · Opus 5.5 · xhigh` (model and effort only when known).
- Details: `Model: claude-opus-5-5 · effort xhigh`.
- `filter.js` `haystack` adds `model_label` and `effort`.

## 10. Error handling

- The tap swallows every error of the recording step; the original command always runs.
- `limits.py` never raises; a broken source drops only its own windows.
- `settings_merge` raises `MergeError` on an unexpected `statusLine` shape and changes nothing; `install.sh` stops with
  the existing message.
- A failing `LimitsReader` in `snapshot()` is logged and yields `"limits": null`, like a failing live map; the UI
  then shows `Claude limits: unavailable`.

## 11. Testing

`unittest`, same style and helpers as the existing tests:

- `tests/test_statusline_tap.py` (run as a subprocess with a temp data dir): stdin reaches the original command
  unchanged; its stdout and exit code pass through; no command → empty output, exit 0; the session's file is written
  on change and when older than 60 s, not otherwise; an invalid `session_id` records nothing; invalid JSON, missing
  `rate_limits` and an unwritable data dir still run the original command.
- `tests/test_settings_merge.py`: wrap with an existing status line (other keys kept), wrap without one, idempotent
  re-install, unwrap with and without a stored command, unwrap of a foreign status line, invalid shapes raise.
- `tests/test_limits.py` with an anonymized `cachedUsageUtilization` fixture and a captured status line input: an
  idle session's lower value never beats a working session's higher one, a later window beats an earlier one, the
  same-window tolerance, expired windows dropped, per-model window, extra usage in major units, account mismatch
  ignored, an unparsable `~/.claude.json` keeps the last good data, old session files deleted, levels at the
  thresholds, reset message formats, malformed inputs.
- `tests/test_sessions_parse.py`: model and effort taken from the last main-chain response, `<synthetic>` and sidechain
